    Executive summary

    The Atheria Law AI Working Group has a working tracker of AI litigation, regulation, and insurance coverage — a single-file prototype with 150+ curated items across the leading public trackers, plus a coverage-overlay analysis (line + likely trigger + likely exclusions in play) that no third-party tracker offers.

    Three things make it defensible against existing trackers:

    • Coverage overlay. No tracker in the market pairs case-level metadata with coverage-line, trigger-clause, and exclusion analysis. That's the actual work AI policy-wording attorneys do — captured in structured form.
    • Data-center vertical. No AI tracker has depth here; no data-center tracker has AI-legal depth. The intersection is exactly this firm's practice.
    • Editorial voice. The Pulse and Case File narratives are written from an underwriter and policy-wording perspective, not an academic one.

    The question this page answers: at each level of investment, what deliverable does the firm own, what does it cost to run, and what value comes back?

    Revision note. This memo was rewritten after an architecture review. The earlier version specified a custom web application (Next.js + PostgreSQL) built in presentation-first tiers, costing 100–160 hours before the tool could update itself. That architecture existed to satisfy one requirement — private notes attached to case records — which implied user accounts, which implied a server. The Claude artifact runtime turns out to provide authenticated, per-user-private storage directly. Removing the server requirement collapses the build to roughly a third of the effort and reorders the work so the tool becomes self-updating first rather than last. Cost figures throughout have been revised down accordingly.

    What "insurance overlay" means concretely. Every case in the tracker carries three structured fields no other tracker captures:

    • Lines of insurance likely to respond — Tech E&O, Cyber, D&O, Media Liability, EPL, GL, Product Liability, AEC Professional Liability, Lawyers' Professional Liability, etc.
    • Likely trigger clauses — wrongful act, personal-injury offense, copyright-infringement offense, security failure, employment-practices wrongful act, statutory-violation coverage, etc.
    • Likely exclusions in play — IP exclusion, bodily injury (broad form), contractual liability, statutory penalties, prior acts, willful conduct, silent-AI exclusions being filed by carriers, etc.

    This is the actual analytical work insurance-coverage attorneys do when advising insurers on AI-related claims. Capturing it in structured form — searchable, filterable, cross-referenced against filings — is what turns a case tracker into a coverage tool. It's also the layer that supports the eventual white-label licensing path in the commercial ladder below.

    How the architecture works — and why it costs so little

    The design separates three things that the earlier plan had fused together. That separation is what makes the tool cheap to run, cheap to change, and able to update itself.

    Three planes, decoupled

    • The data. Case records live as structured files in a private repository, split by year. Every change is versioned and reviewable, the way a document management system tracks revisions — but automatically.
    • The pipeline. Scripts that fetch from court and regulatory sources, remove duplicates, and propose additions. These run on free infrastructure on a schedule. No server to maintain.
    • The presentation. A template that compiles the data into the tracker interface. Roughly 3% the size of the current combined file, so changing how something looks no longer means touching the entire corpus.

    The current tool is one 550KB file in which case data and application code are interleaved. That is workable at 263 items and becomes unmanageable well before 1,000.

    The weekly loop

    Once Stage 2 is in place, the recurring rhythm is:

    • Monday, automated. The pipeline pulls new filings from CourtListener and the Federal Register, discards duplicates and irrelevant matter, and opens a proposed batch for review — for example, "12 new items: 4 IP · 3 sanctions · 2 data-center · 3 regulation."
    • Monday, Nick. Review the proposed batch, correct or drop anything wrong, approve. Target: 20 minutes.
    • On approval. The tracker rebuilds and republishes automatically.

    Nothing reaches the published tracker without attorney approval. The review step is the editorial gate, and it is deliberately the only recurring obligation.

    Why there is no server bill

    The earlier plan budgeted for web hosting, a managed database, and an authentication system — the standard cost of a custom application. Those existed to support one feature: private notes attached to case records.

    The Claude artifact platform provides all three directly. Every viewer is an authenticated member of the firm's organization, and the platform gives each viewer a private storage area that the tool's own owner cannot read. That is a platform guarantee rather than a policy promise, which is a stronger position for attorney work-product than a self-hosted database would be.

    Two note layers become available at no infrastructure cost:

    • Team notes — shared annotations visible to the working group.
    • Private notes — individual work-product, visible only to its author.
    The one tradeoff: a tracker that uses this storage is organization-internal and cannot be published to the open web. That forecloses the public-microsite option for this version. If a public edition is ever wanted, it is a second build from the same data with notes omitted — inexpensive, but worth deciding deliberately.

    Where the operating cost actually goes

    The only meaningful recurring cost is the machine-drafting layer at Stage 3: reading new filings and producing draft summaries and coverage analysis for review. Four design choices keep it small:

    • Filter before analyzing. Rules based on source, court, date, and keyword discard roughly 80% of candidates at no cost, before anything is sent to a model.
    • Match the model to the task. A fast, inexpensive model decides whether an item is relevant; only survivors go to a more capable model for analysis.
    • Process in batches. Weekly ingestion is never time-sensitive, which qualifies it for substantially discounted batch processing.
    • Reuse the stable instructions. The classification vocabulary is large and unchanging, so it is cached rather than re-sent on every call.
    Correction to the prior estimate: the earlier version of this memo put this line at $1,800–$3,600 per year. That figure assumed no filtering, the most capable model on every item, and no batching or caching. With the design above the realistic figure is in the low hundreds of dollars per year — roughly an order of magnitude lower.

    Where the money would go if we tried to do everything

    Two features get asked about most: SERFF filings ingestion and data-center automated ingestion. Both would be uniquely valuable. Both sit at Stage 4 because the underlying data is genuinely hostile to automation. Here's why in plain terms.

    SERFF filings ingestion

    What insurers file with state DOIs — the earliest signal of new AI-related policy wording.

    The value would be enormous: seeing every insurer's proposed AI exclusion, endorsement, or rate change in real time. No competitor tracker has this.

    What makes it a Stage 4 project:

    • Not one system, but 51. Every state (plus DC) runs its own SERFF implementation with a different search interface, filing categories, and approval workflow.
    • Almost no APIs. Most states require scraping web forms; some IP-block automated access.
    • PDF-heavy. ~90% of filings arrive as PDFs. Extracting the actual policy wording requires PDF extraction plus LLM reading.
    • Terrible signal-to-noise. Most filings are routine rate changes. Isolating AI-related ones means reading filing descriptions with an LLM — millions of tokens per year to pull the ~2% that matter.
    • Regional exceptions. California uses a partially separate system (CDI); NY DFS has its own posture.
    • Confidentiality holds. Some filings are marked confidential and not publicly available at all.
    Realistic to build well: 3–5 months of dedicated engineering ($40K – $75K) plus ~$100 – $200/mo ongoing LLM triage. An order of magnitude larger than the self-build tiers.
    Pragmatic interim alternative: manual quarterly SERFF sweeps by a paralegal or junior attorney across 3–5 priority states (NY, CA, IL, TX, FL), ~10–15 hours per sweep. Delivers roughly 60% of the value at a fraction of the cost.

    Data-center automated ingestion

    Hyperscale project activity, community opposition, and municipal legislation at the county level.

    The value would be enormous for the AEC PL and environmental practice — knowing every hotspot before clients do.

    What makes national coverage a Stage 4 project:

    • ~3,000 counties. Each posts agendas independently, with no standardization.
    • The "data center" fact is inside the PDF, not the title. Meeting agendas rarely announce the subject; you have to read the packet.
    • OCR reality. Many county PDFs are scanned images, not text-native. OCR quality varies widely.
    • Court filings scattered. Community-opposition suits live in every state's own e-filing platform.
    • Utility interconnection queues are at ISO level. PJM, MISO, ERCOT, CAISO — accessible but heavily interpretation-dependent.
    • The good subscription trackers are gated. datacentertracker.org and DataCenterHawk do most of this work and charge for access.
    National coverage, built well: 2–4 months of engineering ($30K – $60K) plus ongoing processing and $6K – $15K/yr in subscription data feeds.
    Revised assessment — this was previously too pessimistic. The earlier memo treated data-center ingestion as all-or-nothing. It isn't. Once the Stage 2 pipeline exists, adding scrapers for the six to eight counties that actually matter — Loudoun, Prince William and Fauquier in Virginia; Licking County, Ohio; Coweta County, Georgia; Maricopa County, Arizona — is incremental work measured in days, not months. It is national coverage that is out of scale, not useful coverage. Reclassified from Stage 4 to an ongoing increment after Stage 2.
    Interim option either way: subscribe to datacentertracker.org (~$4K/yr) plus a weekly ~2-hour attorney synthesis pass. Delivers roughly 70% of the value immediately with no engineering at all.

    Curation labor

    Coverage-line + trigger + exclusion analysis is the differentiator. It doesn't automate away.

    Even at Stage 3, someone has to make the final editorial call about which developments matter and what the coverage analysis says. Machine assistance cuts the weekly load substantially — from roughly 3 hours (all human) to about 20 minutes of review plus 15 minutes of editorial — but never to zero. This is the reality of the coverage-overlay moat: it is judgment work, not classification work.

    Positive framing: that irreducible attorney time is exactly what makes this defensible against pure-tech competitors. The moat is the editorial voice, not the pipeline.

    Commercial models

    Four paths, unlocked at successive tiers. Not mutually exclusive — many mature tools carry two or three simultaneously.

    Available now

    Internal tool + BD asset

    Sharpens the AI practice, deepens client relationships, generates content for firm publications. Value shows in matter generation and retention. Hardest to quantify, likely the most reliably recovered ROI. Available today.

    Unlocks at Stage 2, best at Stage 3

    Insurer-sponsored consortium

    Two or three insurers each contribute ($25K – $50K each) toward Stage 4 features (SERFF, national DC coverage) in exchange for early access, feature-set input, and a private data cut. Gives the firm channel-partner relationships with named carriers. Underwrites Stage 4 without firm capital.

    Unlocks at Stage 3

    Subscription product

    Target market: mid-market AI-practice firms, insurance brokerages, model-developer general-counsel offices. Priced ~$400 – $800/user/month. Break-even at 30 – 60 seats. Requires real go-to-market spend beyond what's modeled in the tiers above.

    Unlocks at Stage 4

    White-labeled tracker

    Licensed to insurers or brokerages under their brand. Revenue-share or flat license fee ($50K – $150K/yr per licensee). Highest-margin path but requires Stage 4 data completeness. Depends on SERFF and national DC ingest already being in production.

    Architectural note

    The public-edition question

    Because the notes feature makes this version organization-internal, a public-facing edition would be a separate build from the same corpus with notes omitted. That is inexpensive to produce but should be a deliberate decision rather than an assumption — it affects whether the tool is positioned as an internal asset or a marketing surface.

    Risks & mitigants

    Data reliability
    Seed items require Westlaw verification before client-facing use; ingest quality determines credibility. Mitigation: strict primary-source citation on every item; no downstream distribution of unverified content.
    Competing trackers
    GWU, Orrick, Charlotin, ChatGPT-Is-Eating-the-World. Mitigation: the coverage overlay is a defensible moat; positioning is complement, not replacement — we credit source trackers explicitly.
    Effort overrun
    Build phases running long is the classic failure mode, and attorney hours are the scarce resource here rather than cash. Mitigation: phases are independently useful and independently abandonable. If Phase 1 lands and Phase 2 stalls, the tool is still better off than today. No phase is a sunk prerequisite for a benefit that only arrives later.
    Platform dependency
    The architecture relies on the Claude artifact runtime for hosting, authentication, and note storage. If that platform changes materially, those pieces need replacing. Mitigation: the corpus itself lives in a private git repository in an open format and is fully portable. Only the presentation layer and notes are platform-coupled; the asset that took real work to build is not.
    Source API changes
    CourtListener, Federal Register, and similar feeds can change formats or terms. Mitigation: one self-contained module per source, so a break is isolated and repairable in hours; the pipeline continues on remaining sources meanwhile.
    Machine-drafted error reaching a client
    Stage 3 introduces drafted analysis that could be wrong. Mitigation: per-item review status, with pending items excluded from client-shareable views by default. Nothing publishes without attorney approval of the weekly batch.
    Regulatory volatility
    The Trump EO reset in Jan 2025 demonstrated how fast the ground moves. Mitigation: the tracker's editorial voice becomes more valuable in flux, not less — volatility is a growth driver.
    Attorney bandwidth
    Curation labor is real, even at Gold. Mitigation: LLM-drafted Pulse mitigates weekly overhead; ad-hoc research load stays attorney-manual and is billable to matters.
    Partner engagement
    If firm partners don't actually use the tool, the BD value evaporates. Mitigation: monthly firm-wide "what moved this week" briefing driven from the Pulse; track engagement as a KPI.
    Vendor / API dependency
    CourtListener, EDGAR, LegiScan may change terms or degrade. Mitigation: sources are diversified across three or four upstream feeds per topic; no single point of failure.

    Recommended path

    A staged commitment that lets the firm evaluate at each tier before releasing the next capital tranche.

    1. Complete

      Stage 1 — hand-curated prototype, live and shareable

      263 items with coverage analysis, six views, published and viewable at a link. Circulate to partners for reaction. Zero incremental cost.

    2. 2–3 weeks · 8–12 hrs · no cash cost

      Separate the data from the presentation

      Nothing partners will see changes. Case data moves out of the single monolithic file into structured, versioned records; a build script reassembles the tracker. This is unglamorous and it is the highest-leverage step available — it makes every later change roughly eight times cheaper and stops the file being risky to edit as the corpus grows.

    3. 3–4 weeks · 12–16 hrs · no cash cost

      Stage 2 — the tool starts updating itself

      Automated weekly pull from CourtListener and the Federal Register, with new items arriving as a batch for approval. This is the decision point that matters most: after it, the tracker stays current on about 20 minutes of attorney time per week instead of three hours. Everything after this is improvement on a working system rather than a prerequisite.

    4. 3–4 weeks · 14–22 hrs · $150–500/yr

      Stage 3 — machine drafting and the notes layer

      Draft summaries and coverage analysis prepared for review rather than written from scratch; per-item review status so machine-drafted and attorney-verified records are visibly distinct; private and team notes attached to cases. Worth committing once Stage 2 has run for a few weeks and the batch quality is known.

    5. Ongoing, as useful

      Breadth and polish, in any order

      Additional sources (Regulations.gov, EUR-Lex, Open States, EDGAR); scrapers for the six to eight data-center counties that matter; richer visualizations. Each is independently valuable and none blocks the others. Sequence by what the practice needs at the time.

    6. When Stage 3 is proven

      Stage 4 conversation with insurers

      Approach two or three carriers about co-funding SERFF ingestion and national data-center coverage. Requires a working tool and a demonstrable usage record. Firm capital commitment does not need to scale past Stage 3 — Stage 4 is contingent on outside money.

    Total firm commitment through Stage 3: roughly 35–50 hours of attorney time and under $1,000 in the first year. The earlier version of this memo asked for 260–400 hours and $22,000–$32,000 to reach a comparable point.

    Open questions for the partnership

    1. Ownership. Does the firm own the tool as a firm asset, does the AI Working Group own it internally, or is it structured as a spinout? This has tax and IP implications that ripple through everything else.
    2. Who gets access. The notes layer distinguishes viewers who can read from those who can edit. Which attorneys should have edit rights, and does anyone outside the Working Group get read access?
    3. Public edition, yes or no. The notes feature makes this version organization-internal. If a public thought-leadership edition is wanted, it is a second build from the same data — cheap, but it should be a deliberate decision rather than a default.
    4. Editorial governance. If more than one attorney maintains the Pulse or writes team notes, we need standards — voice, what warrants inclusion, how disagreements are resolved.
    5. Verification posture. Stage 3 introduces per-item review status. What does the firm require before an item can appear in something client-facing — attorney skim, or full verification against primary sources?
    6. Client-disclosure posture. What is shareable with clients as-is, versus what requires firm review before external send? Should shared views carry a firm disclaimer or the Working Group's?
    7. Insurer relationships. Are there two or three specific carriers we would approach for Stage 4 co-funding? Timing matters — too early reduces credibility; too late gives up runway.
    8. Attorney-time accounting. Should the weekly review be booked as marketing/BD overhead or absorbed as professional development? This affects both partner incentives and internal cost recovery.
